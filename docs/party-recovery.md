# 3.8 保存層向けの編成検証・復旧候補

入口は`src/game/party/index.ts`。`recovery.ts`が現在編成とプリセット集合の診断を提供し、`repair.ts`が旧プリセットと共通のID移行・依存ノード除去・装備配分・差分生成を担当する。カタログと進行は事前検証済みのものを渡す。

## 現在編成の復旧

`previewCurrentPartyRecovery(content, input, context, migration?)`は未知JSONの現在編成から候補を返す。人物順・枠数・値の構造が破損していれば`ok: false`で拒否し、勝手に不足枠や人物を補わない。

構造が読める場合は、保存層が選んだ明示ID対応表を適用してから修復する。対応表自身のキーだけを使い、継承プロパティを移行として扱わない。

| 不整合 | 候補の規則 |
| --- | --- |
| 未知ジョブ | `kind: initial-party`で3人の初期ジョブ・初期習得・初期装備への復帰候補を提示 |
| 個人予算超過 | 移行後の本人の使用ポイントを確認し、本人の習得をすべて解除。他人の習得は維持 |
| 未知／他職ノード・前提欠落 | ノードを除外し、前提を失う子孫も連鎖除去 |
| 未取得・削除済み装備・所持数超過 | 人物1→2→3、枠0→5の順で所持数まで保持し、残りをnullにする |
| その他の不整合 | 残存問題として返す。未定義の修復は行わない |

`previewInitialPartyRecovery`は初期編成への戻しを明示的に選んだ場合にも使える。初期定義の装備を共通配分で再検証するため、品物を追加配布せず、現在の所持数から各人物の装備を構成する。討伐・未使用ポイント・プリセットを初期化するAPIではない。

結果は`party`、`changes`、`issues`、`kind`を持つ。`ok: true`は候補を生成できたという意味で、適用可能とは限らない。`issues`が空であることを確認し、差分をユーザーへ提示してから保存層で確定する。候補生成は戦闘中の編成適用を許可しない。

旧プリセットの`previewPresetRepair`は未知ジョブと予算超過を残存問題にする従来契約を維持する。通常呼出・修復呼出の拒否規則も緩和しない。現在編成の復旧だけに、初期復帰候補と予算超過時の全解除を追加した。

## プリセット集合の読み込み診断

`inspectPresetCollection(content, input, context, migration?)`は最大20件、一意ID、各件の管理情報と編成を確認する。配列以外は拒否する。並び順の変更、削除、修復、保存は行わない。

- `issues`は件数・重複ID・管理情報の集合診断。`metadataValid`はこの一覧が空かを示す。問題があれば保存層が復旧方針を決める。
- `entries`は全件のインデックス、原本の独立コピー、管理情報の問題、編成の問題、`callable`を保持する。重複IDの全該当件は呼出不可。
- 旧編成だけが無効なら`metadataValid: true`のまま、その件の`partyIssues`と`callable: false`を返す。正常な現在編成・進行のロードを一律に止めず、原本を保持して無効表示できる。
- 明示移行後の候補で呼出可否を判定しても、`original`は旧データを保持する。移行版の選択、移行保存、原本バックアップは保存層の担当。

`validatePresetMetadata`は単件の管理項目だけを確認する入口として公開する。編成までの単件検証は従来の`validatePreset`を使用する。

## 保存への接続と検証

APIの入力は編成と進行コンテキストだけであり、進行・プリセット原本へ書き込まない。保存層は候補の再検証、差分確認、版照合、明示確定、current／previousの保存をタスク4で接続する。

`recovery.test.ts`で本人だけの全解除、未知職の初期復帰、依存解除、共通装備配分、明示移行、所持数の非増加、構造破損と残存問題、旧プリセットとの規則差、個別無効判定、重複ID・件数超過・管理情報破損、原本の独立性を検証する。既存のプリセットテストも共通化後に維持する。
